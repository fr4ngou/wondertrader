# 唯一1.1.2实时入口的实际异常退出

状态：investigating。等级：主要；环境：模块B隔离开发验证，合成行情/基础资料/券商替身；责任：模块B。日期：2026-10-29。新增生产WT核心修改0、真实券商调用0。

## 症状与处理边界

`build/ms-retained-cta-001/main-001`运行唯一1.1.2策略，经原CTA、原数量执行链提交一次替身卖出200股后，原生Python进程以`0xC0000005`退出。原始退出使NRT-R18完整实时入口验收失败；该候选保持开发验证状态。

此前将本次退出称作“WT线程问题”，并用用户暂停潜在框架问题研究的决定解释继续搁置，归因和处理均不成立。用户本次明确要求定位已经发生的异常退出。本记录只调查这次实际故障及直接相关链路；历史框架候选保持原状态，生产核心行为修改继续按明确授权处理。

## 已复现的失效链

隔离调试继续加载同一原Runtime、同一安装Python和原QA Parser。调试器仅附加由本次受管实例返回的PID，在已核对字节的原任务指令处控制一次线程停顿；恢复原指令后，容许其他线程按原方式继续执行，再恢复该任务。断点及暂停均限于独占诊断进程，不产生生产代码修改。

1. 后台任务已查到一个有效持仓条目，准备从条目读取对象指针。此时表内有2个条目，记录的条目地址位于当前vector范围。
2. 正式入口计算完整八证券目标，后续报价处理使原组合表扩展为8个条目。vector搬到新地址；被暂停任务仍保存旧条目地址。
3. 调试器读到vector已经搬动，恢复后台任务。任务从旧条目读到空对象指针；`RBX=0x18`，随后写地址`0x18`发生访问冲突。
4. 两次均在原Runtime的RVA `0xab620`退出，与原始事件的模块和指令完全对应。

这证明当前运行库在本次正式入口的条目增长条件下，容器条目引用可因搬动而失效。对象内部锁开始生效前，条目引用已经失效；原对象锁无法保护承载该引用的容器存储。当前固定源码中，这个容器由`ankerl::unordered_dense::map`的vector承载。

**证据边界：两次复现显式控制了线程交错。首次自然崩溃只有同模块、同指令及相同条目增长场景，缺少同次现场，仍不能声称已直接证明首次故障采用了完全相同的交错。** 当前库含既有已批准差异；本轮没有重新取得纯上游框架产品运行的结论。

| 场景 | 结果及限制 |

| `schedule-002`暂停上限18秒 | 实际检测到2→8条目搬移后立即恢复；旧条目越界，目标指令AV，4次查询/1次替身卖出 |

| `probe-001`至`probe-006` | 原Runtime加QA Parser异常观察，6次首代正常；Parser属于诊断变体，范围单列 |

两次AV均保留第一机会和第二机会异常寄存器，以及私有dump。带外部异常信息的dump API失败后，成功生成不含异常流的dump；异常寄存器另存调试收据。基于dump的栈扫描只记录候选返回地址，没有当作完成展开的调用栈。原始dump保留在受控build目录，正文只给去敏字段。

冻结结论：`build/ms-retained-crash-001/CONCLUSION-001.json`，SHA256 `48ce26b7d80c353eeeb54e696aa9e147067d5d546b1d538e43bc8f7247812120`。该收据关联生产身份、本批诊断源码摘要、MAP及三次交错观察原件；诊断源码快照位于同根`qa-source`。

## 单独记录的主动退出

`repro-001`、`debug-001/002`的第二代，以及`debug-007`的首代发生主动错误退出1。`debug-002`捕获的C++异常为自有`execution_host_configuration`；进程错误路径报告`session=4, host=3, plugin_error=10`，原因摘要对应自有`qmt_http_exchange_failed`常量。

后继读到`debug-002/POSTFLIGHT.json`的`proxy_first_error`为QA `_EventProxy` 的`actual Host page capacity`：两代夹具提高了请求预算，仍保留128页旧上限。QA已将事件页上限与2048请求及既有8MiB总字节预算关联；`main-003/004`完成两代。`debug-007`代理错误为空，其一次交换失败原因仍为unknown，前述容量原因只覆盖有对应原件的运行。

此后还定位到二代QA只重放旧分钟，原WT保留的闭合bar使其等待后继调度。夹具增加新的1003闭合分钟后完成二代；这项等待与HTTP失败分别记录。当前没有证据把两者归为原持仓条目失效。

## 后继实际关闭异常

股票执行单元的关闭异常与前述运行中`0xab620`故障分别调查。`stock-main-003`及新自有关闭候选`stock-main-005`均捕获执行已释放内存的`c0000005`。后一例已完成一次替身卖出200及后继收敛，关闭时原进程exit2；dump栈顶候选返回地址为`WtExeFact.dll+0x1baff`。固定原工厂对应位置是股票单元析构的`_comm_info->release()`调用；栈扫描结果按候选返回地址保留，没有当作完整展开栈。

固定原工厂的独立初始化/销毁实验记录于`build/ms-stock-reference-001/RESULT.json`：观察引用使初始计数为2；原单元init后仍为2（应为3），销毁后为1（应为2）。源码链为原BaseDataMgr借出资料、单元缓存retain、`get_minOrderQty`对第二次借用release、析构再次release。这证明此固定股票组件存在一次引用缺额；无需引入线程交错即可复现该计数错误。[既有提案](../migration/native-stock-metadata-ownership-proposal.md)保持未实施，新框架源码修改为0。

实际关闭还暴露自有边界错误：此前Standard.close在Local/单元仍存活时返回成功，Session随后生成clean，最终析构才发生异常。自有P24现已把Local/Adapter销毁纳入close，并在它们完成后释放行情/上下文依赖、生成恢复证明。`stock-main-004`曾在native003完成两代自然exit0；native004的`stock-main-005`再次失败，因此当前不能宣布股票退出故障修复。新候选失败后无clean、无成功closed收据，Host/Source/server/proxy六项物理关闭全部为true。

`sellable-004`同候选关闭exit2、SDK0且无clean，未附异常调试器，具体原因保持unknown。`p24-unclean-003`复制`stock-main-005`留下的5份金融文件，缺clean的恢复在Ready前拒绝；4查询、SDK0，原件及副本共10项SHA不变，完整回收。当前结果及身份见[唯一实时桥与关闭边界证据](../evidence/2026-10-29-retained-cta-and-close-boundary.md)。

## 恢复与后续动作

所有本轮受管错误进程已经回收；对应POSTFLIGHT中的Host关闭、Host/Source资源关闭、Source关闭确认、HTTP server join及proxy join均为true。两次受控AV的实际替身卖出都为1次；真实SDK调用为0。原异常根、金融文件、命令身份及dump保持，尚未完成异常状态恢复资格。

独立复核确认受控条目失效机制的证据成立，并指出测试工具在`start()`附加后抛错时，局部变量尚未取得调试器对象，清理会漏调`close()`。已将构造赋值与`start()`分开；`DEBUGGER-START-FAILURE-001.json`记录实际附加后注入异常，调试器detach/join、原生自然exit0和Host/Source/server/proxy关闭全部通过，SDK调用0。该修改仅影响QA清理，原交错实验快照与结论保持。

前批Python语法检查通过；当时`project.py check`因共享任务两份调整文档未索引而失败。该历史结果按当时输入保留，后继静态检查见最新证据。

当前完成运行中故障位置与相符机制复现、股票组件引用缺额及实际关闭现场核对、自有关闭证明边界修正。首次自然事件的同次归因、股票完整退出及当前候选两代仍开放。后续修复限定实际故障对应责任层；已有撤回的事件串行方案和额外保存方案继续保持原状态。
