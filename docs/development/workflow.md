# 开发流程规范

类型：长期规范。适用范围：功能、修复、重构、依赖升级及配置行为变更。

## 工作树与主干

初始克隆的主目录固定检出本地 `master`，用于同步、查阅、集成和发布核对。功能、修复、重构、依赖、配置和文档开发均在主目录之外的任务 worktree 进行。 主目录和新建的任务 worktree 使用完整检出，确保代码、文档及本地验证引用的原件齐备。

1. 开工前从主目录确认当前分支为 `master`，获取远端 `master` 并核对历史。远端更新可快进时同步到本地 `master`。本地包含远端时以最新本地 `master` 为基线，保留已集成提交。两边分叉时在独立集成 worktree 对齐并验证，主目录沿本地 CI 快进采用结果。
2. 新任务从已核对的本地 `master` 创建独立 worktree，任务分支默认使用 `codex/` 前缀。续接任务使用该任务原 worktree。编辑前核对 worktree 路径、分支和基线。
3. 合入前重新核对本地 `master`。候选基线落后时在任务 worktree 更新并重验。通过本地 CI 快进主目录的 `master` 后，按[Worktree收尾](#worktree收尾)手动清理已完成任务的临时目录。

## 入口与计划

1. 执行 `python -B scripts/project.py start`，查看工作树和相关规格，先按[WonderTrader能力目录](wondertrader-capabilities.md)及[复用规则](wondertrader-reuse.md)核实原生支持与边界，再沿模块入口核实完整调用链；按[缺陷记录与检索规则](../runbooks/incidents.md#开发缺陷记录与检索)查阅相关历史问题。
2. 明确预期结果、根因假设、事实所有者、影响范围、关键决策、步骤和验收标准。计划保留这些内容，调试尝试放临时记录。
3. 已确认需求直接实施；改变预期行为先更新原规格。职责、权限、事实所有权和恢复语义变化按[方案规范](design.md)形成适用决策。

## 会话协作

分工以完整模块为单位。创建或续接开发者目标时，写清模块边界、文件与接口所有权、可观察的验收结果、合入方式及沟通约束；开发者按目标独立推进。

跨会话消息仅用于以下事项：

- 模块完成：一次交付最终行为、源码身份、验证证据、合入入口及剩余风险。
- 真实阻塞：明确接收方需要执行的动作，以及该动作阻塞的业务结果。
- 共享资源冲突：需要协调的文件、接口、服务或运行环境及建议处理方式。
- 必须决策：需要接收方或用户决定的具体问题及可选方案。

同一问题的发现、根因和处理要求合并发送。已报告的问题仅在处理要求发生实质变化时追加消息。普通进度、逐项验证结果、重复状态、催问和收悉确认保留在各自会话；“无需回复”不构成发送理由。接收方按自身工作阶段处理必要交接，保持独立开发。

协调者通过紧凑状态快照和最终交付跟进任务，按真实依赖安排沟通。用户清除开发者目标后，该目标保持清除状态，后续分工沿用户授权重新设置；收尾交接集中发送一次。

后续创建开发者目标时，将下列约束直接写入目标正文，与模块目标和验收标准一起提交：

> 独立完成所分配模块。跨会话仅发送完整交付、需要对方行动的真实阻塞、共享资源冲突或必须决策的事项；同一问题合并发送，普通进度留在本会话。用户清除目标后保持清除状态。

## 主路径优先

1. 将目标拆为职责完整、可独立验证的业务切片，先连接实际入口、生产者、消费者和存储，跑通该切片的完整调用链。
2. 每个切片同步完成必要验证；设计阶段明确影响架构选择、数据正确性和副作用安全的异常与恢复要求，随相关实现验证。
3. 切片形成可审查结果后进行相应评审与修正；集成完成后执行跨切片验收和交付检查。

开发中优先解决直接阻断主路径的问题。阶段进度以已可运行的功能和实际业务结果汇报；纯测试数量、局部契约和审查材料分别记录其范围。

复用已有测试、实际入口和运行记录确认业务结果。缺陷修复尽早建立原触发条件的回归验证，新增或修改逻辑的必要测试随对应切片完成；测试有效性和范围按[验证规范](verification.md)核对。账户与运行模式确认、未知副作用核查等实际操作前置条件沿原业务要求执行。

当完整恢复或自动化显著扩大实现范围时，先交付职责完整、状态可核实的最小可用流程；列明适用条件和未覆盖能力，再按实际需要扩展。沿用已有入口、查询与状态管理，增加的持久状态和分支须对应明确的业务缺口。

## 实施

- 每次变更围绕一个明确目标，以可验证的完整切片保持接口、状态变化、消费者和错误语义一致，并包含必要验证和文档。较大改造拆成可独立评审的完整步骤；无关重构、格式整理与功能修改分别组织。完成范围由业务要求决定，切片用于安排实施和评审。
- 修复先保留原触发条件，沿输入、状态及副作用定位根因，在责任层统一处理并清理失效重复逻辑。
- 重构明确保持的行为及验证方式；新旧实现并存时写明切换、观测和旧实现退出条件。
- 可变业务事实使用权威配置，协议常量集中定义。配置修改包含范围、默认值、权限、生效与恢复规则。
- 并行任务先明确公共契约和文件所有权；共享文件按最新快照合并，保留其他任务改动。
- 先检索现有实现和公开接口，再决定新增模块。新增持久化或跨层协调说明现有能力缺口、收益及运维成本。

## 验证与评审

按[主路径优先](#主路径优先)随切片开展验证与评审，按[验证规范](verification.md)覆盖正向、异常、恢复和受影响调用链。复用输入仍有效的证据，代码、环境或契约变化时重验受影响部分。

编写核验脚本前，读取实际公开接口、返回结构、缓存布局和已验证构建命令；脚本字段及路径须有源码或实际结果依据。同一组源码、依赖、配置和运行输入已有有效验收时，复用该结果；新增变更只重验受影响链路。每个完成的功能增量统一打包，避免相同输入反复构建、安装和全面回归。

送审资料包含最终规格、源码差异、验证入口、结果及限制。审查分别核对规格符合性、代码规范、事实所有者、异常恢复和职责完整性。涉及交易副作用、并发、状态持久化、权限或发布切换时，由独立审查者核对关键路径；审查结论关联实际源码身份。

发现问题先修正，再重验受影响条件。保留明确风险接受记录及相应权限，代码审查通过与运行资格分别登记。

审查范围记录为 full（首次或规格/公共契约/风险边界变化）、delta（同一要求内局部修复）、reuse（当前输入已有有效报告）或 none（适用规则未触发独立审查），逐项说明理由及代码身份。delta 由审查者确认全部适用要求的影响范围；历史通过结论按实际输入核实。

独立审查资料以最终规格、适用规则和源码为依据；任务过程、历史评语和开发者自评保存在独立记录。审查按要求给出 complete/gap/unknown、位置和证据，缺失行为证据明确列出。当前自动分类与收据校验能力以实际工具交付为准，文档中的流程要求不表示已有自动门禁。

## 完成与回写

任务状态使用 `planned → in-progress → pending-verification / done`。`done` 表示任务要求的验收全部满足；环境缺失、失败或关键入口未验收时记录 `pending-verification`、原因及下一步。

按[实际影响选择文档维护量](documentation.md#按影响选择维护量)，只回写发生变化的权威正文；需要跨会话续接或已登记活动任务的续接状态变化时维护对应任务记录/NOW。项目采用事实或目标变化时，按[当前快照维护](documentation.md#当前快照维护)更新 CURRENT/TARGET 对应主题。小任务的验证结果可留在已有提交、PR 或交付答复中。使用 `python -B scripts/project.py check` 验证本地文档完整性。功能交付以相应运行环境中的真实入口、核心数据、主要操作和异常状态验收为准。

汇报分别说明已开发、主路径已验收、已合入、已交付及已部署的范围，并列出尚缺的具体功能和下一动作。仍有功能缺口时按该缺口汇报，完成时间以实际进展为依据。

## Git 与交接

本地候选使用[CI合入入口](../runbooks/local-ci.md)：自动运行适用检查，核对最终源码与结果身份，再合入本地master。此流程与远端托管平台独立，发布和真实交易沿各自授权执行。普通Git命令未安装额外自动钩子。

使用明确文件清单暂存和提交，提交前核对最新工作树、差异及敏感内容。保留上游许可证及来源。合并、推送、打标签、构建制品、部署和交易授权分别解释，依当前任务授权执行。

共享集成由明确的单一集成者执行，先核对最新基线及公共契约，再组合各任务结果。跟进上游与控制自有差异遵循[上游规范](upstream.md)，避免将框架升级与无关业务变化混在同一候选中。

交接说明最终行为、源码身份、验证依据、剩余风险和下一动作；临时尝试不写入长期规范。

## Worktree收尾

使用临时worktree开发的任务，在代码合入本地master后，由该任务开发者在同次收尾中手动核对并清理worktree。这是开发工作约定；CI程序继续负责检查和合入，清理作为后续人工收尾执行。源码合入、资料保留和工作树清理共同构成任务收尾。

1. 核对任务HEAD已包含在master中，逐项处理独有提交、未提交改动和未跟踪成果；需要保留的代码先合入，证据与本机设置转存到主工作区或长期受控目录。
2. 核对运行进程、配置和其他会话对该工作树的依赖；依赖先迁移到正式安装、主工作区或长期目录，再清理工作树。保留其他任务正在使用的工作区。
3. 从主工作区执行`git worktree remove <任务工作树绝对路径>`，沿Git正常校验完成删除。Windows下先核实解析后的绝对路径正是本任务工作树。
4. 核对工作树目录已不存在、`git worktree list`已移除该登记，后续命令切回主工作区。删除worktree保持已合入的提交和分支历史。
5. 汇报合入提交、清理结果及保留资料的位置。存在独有成果或运行依赖时先完成转存与迁移，收尾记录保持为未完成并列明具体处理事项；处理后继续完成清理。

主工作区和其他会话的临时工作树由各自任务管理。本规则作为开发收尾执行，不引入交易运行条件或策略上线审批。
