# 上游维护与低冲突开发规范

类型：长期规范。范围：上游跟踪、下游扩展、核心差异和升级审查。

## 分支与版本

`upstream` 保存上游只读来源，`origin` 保存本系统的正式主干与任务分支。发行版本同时绑定下游提交和上游基线；上游 tag、分支、发布包名称和下游 release ID 分别记录。

共享主干保持历史连续；上游升级通过独立分支 merge 到正式主干，保留上游祖先关系。自有功能可以按项目规则 squash 集成，但上游升级合并保留完整 ancestry，以便后续增量合并识别已吸收内容。

未共享、未发布的个人分支可以 rebase；共享主干、已发布提交和发布标签保持身份稳定。冲突恢复使用 merge/rebase 对应的 abort/continue 流程，先核对当前操作与工作区状态。

## 日常修改

- 先查公开接口、插件和配置，扩展代码放在清楚的自有模块或标准插件位置。
- 接入扩展沿框架既有架构，通过插件、公开接口、配置和独立宿主实现。方案先列出复用接缝及消费者，保持上游模块职责与生命周期。
- 修改上游框架源码前，须向用户提交必要性、既有公开扩展机制的具体不足、替代方案、文件/接口范围、架构/ABI/升级风险、验证和回滚方式，并取得用户明确批准。批准范围内使用独立提交及回归，在[覆盖登记](../maintenance/upstream-overrides.md)登记差异与退出条件。批准前保持相关框架文件只读；适配实现继续在既有插件和自有模块中推进，已有差异逐项审查归属和外置可能。
- 功能改动与重命名、全文件格式化、换行转换分开，保留上游编码和目录风格。
- 公共头、序列化布局及回调 ABI 的改变列出所有消费者，验证新旧库组合与重新编译要求。
- 上游修复采用可追踪方式吸收；已由上游提供的等价能力，经测试确认后退出自有重复实现。
- 项目文档和测试使用自有路径。公共构建清单和入口文件尽量只保留集中接线，减少散布在多个上游文件中的环境特判。

## 框架行为的配置分流

框架行为适配由配置明确选择原生路径或适配路径。缺省和显式原生配置均执行原生路径；适配路径须由有效配置显式启用。优先复用已有插件、工厂或模式选择配置，在负责该行为的入口完成单一选择，保留原算法和职责。新增框架源码差异仍按上述审批要求实施。

配置必须说明键名、允许值、默认值、适用实例、依赖条件及选择时机。非法值在启动准入时失败；业务错误沿已选路径处理，交易请求与未知结果保持原命令身份。实例初始化时固定模式；涉及持仓、订单、线程或缓存的切换，通过停止、状态恢复和重启完成。运行期热切换需单独设计状态交接并验收。

验收分别覆盖缺省、显式原生、显式适配和非法配置。原生路径与固定上游基线比较；适配路径覆盖完整调用链、异常及重启恢复。发布和回退材料记录实际生效配置及未决状态处理。测试派生类的单路径验证保留为接缝证据，实际配置选择和原路径兼容分别取得证据。已有框架差异按同一规则逐项登记配置覆盖及待处理项，再形成必要的调整方案。

## 更新与冲突

先读上游变化及已登记覆盖，再进行三方合并。每个冲突核对原基线意图、上游新行为、本系统要求和最终验证；按业务语义整合。自动选择一侧只适用于已证明可丢弃的生成内容，并在记录说明依据。

更新回归按接口、状态、数据、执行、依赖及部署影响选择。与输入匹配的结果复用，基线或行为变化对应补测。上游获取、代码集成、发行打包、部署和交易启用分别登记。

步骤见[上游更新操作手册](../runbooks/upstream-updates.md)，整体方案见[原生发布与上游维护](../specs/native-release-and-upstream.md)。
