# WonderTrader 能力核实与开发规则

类型：长期开发规范。适用范围：系统功能、架构、接入、状态持久化及替代实现的设计与开发。

## 开发前置

先阅读[原生能力目录](wondertrader-capabilities.md)及对应模块正文。为本次需求填写能力编号、固定上游源码/公开接口、配置和数据条件、限制、已验范围与实际缺口。沿宿主→引擎→上下文→插件→存储/外部源核查完整路径，不能只凭接口名、目录、README或自有候选实现判断框架支持程度。

能力分为：原生可复用、配置/插件适配后可用、官方可选子项目提供、存在接口但该路径未实现、尚未核实。源码可定位与目标环境已验证分别登记。尚未核实的相关能力先调查；不能用“未知”证明需要新建模块。

## 实现选择

1. 原生已经提供的能力采用原生实现，配置、调用或字段映射形成最薄接缝。
2. 与旧系统重合的职责采用WonderTrader，旧实现退出目标架构；旧进程、表、消息链或接口形状不作为保留条件。
3. 业务独有算法和语义迁入相应策略、风控或接入扩展，必要的独立业务模块按功能保留。必须证明原生缺口，不能仅因旧代码存在就原样保留服务。
4. 官方可选子项目与C++核心分别登记；采用可选组件需符合运行依赖和产品约束。扩展现有组件优先于重写等价能力。
5. 确认原公开扩展机制不足后才提出核心修改；必要性、替代方案、最小范围、风险、验证和回滚按[上游规范](upstream.md)获得批准后实施。

功能一致性以业务语义判断。例如策略目标与柜台持仓、行情历史与输入冻结、成交日志与未决命令身份分别归属。原生替代不扩大其本来保证；功能缺口也不自动要求另建数据库或第二套权威状态。

## 并发与恢复核实

必须说明对象/线程所有者、调用线程、队列与锁覆盖、回调是否重入、切片生命期、文件或mmap读写者、进程间边界，以及停止准入→排空→join→释放的实际路径。交易恢复核对查询和回报交接、重复/乱序、未决命令与就绪条件；不预设统一数据库事务或自有四快照协议是框架要求。

原样故障、静态风险、源SDK契约和新增宿主需求分开记录。异常路径先使用固定上游和适用配置验证；测试通过只支持实际覆盖条件。性能、全市场容量、热更新和跨进程一致性没有证据时明确待验，禁止套用宣传性能数字。

## 设计与审查必填

| 项目 | 必填内容 |
|---|---|
| 对应能力 | 目录编号、原生模块/符号、固定版本 |
| 复用方式 | 配置、公开调用、插件或必要业务扩展 |
| 重合实现处理 | 旧职责退出项、用户功能承接位置、单一状态owner |
| 实际缺口 | 原生不覆盖的具体语义、源码依据和最小补充范围 |
| 边界 | 时间/单位/状态/线程/存储/生命周期及依赖条件 |
| 验证 | 原路径、替代路径、异常恢复、真实数据和用户入口 |
| 切换 | 现有事实保留、未决操作交接、单入口切换和回退 |

方案缺少上述能力依据时先补调查和文档。审查发现自研重复能力时回到原生接缝重新设计。退出目标架构不等于立即删除历史事实或停用生产；实际切换和清理遵守授权、验证及回滚边界。

## 维护

升级上游或发现新能力时同步目录、模块正文与相关方案，给出固定源码和验证范围。目录维护支持边界，任务记录维护进度；两者不互相替代。
