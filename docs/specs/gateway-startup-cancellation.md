# Gateway 启动取消隔离规格

状态：accepted（隔离实验）；生产资格：pending-verification。

目标：修复 GatewayServer 启动超时后后台线程继续启动的问题。唯一生命周期 owner 为 GatewayServer；调用链为 start → 后台导入/构造 → listen → 发布就绪 → IOLoop → 原异步 drain → 资源清理。候选位于 `build/native/gateway-startup-audit/candidate/`，原 QMT 与运行实例保持只读。

## 要求

- GSC-R1 启动：每次实际启动拥有独立的结果与事件；存活线程期间 start 返回 False，旧线程完全退出后才能创建下一次。旧调用者读取其所属启动结果。
- GSC-R2 超时与停止：start 超时必须先登记取消再抛错；stop 对尚未创建 IOLoop 的存活线程同样登记取消，并按调用者秒级预算等待真实退出。取消不表示线程已退出，无法强制终止卡住的 Python 导入或第三方构造。
- GSC-R3 阶段边界：第三方导入、IOLoop/应用/HTTPServer 构造、listen、状态存储均在生命周期锁外。各阶段完成后检查取消；取消已在上一阶段生效时，禁止进入下一阶段。原 Tornado listen 保留其网络行为。
- GSC-R4 bind 与发布：阶段准入检查与取消使用同一锁。listen 已准入后发生取消时，调用仍可能完成并短暂建立 TCP listener；返回后立即清理并禁止发布就绪或运行事件循环。就绪发布与取消互斥；已发布运行的 stop 继续使用原异步 drain。start 因取消结束时给出明确错误。
- GSC-R5 清理：取消、启动异常、运行退出均由后台线程清理其已创建的 HTTPServer 与 IOLoop；两项资源分别尝试关闭。清理完成后设置 stopped，stop 还须 join 确认线程退出。异常结果与取消原因分开。
- GSC-R6 恢复：只有旧线程退出才允许同实例重启，新启动重置事件、错误、取消和 drain deadline；并发旧调用者不得取消新一代启动。存活的卡住线程继续阻止重启。ensure_running 在同一锁内观察运行资格和代次，并把后续停止、重新启动绑定到该代次；观察之后一旦其他调用者替换代次，旧恢复抛出明确的 generation changed 错误，由调用方重新核实当前状态。该旧恢复保持新代状态，且不会把新代尚未就绪的状态作为恢复成功。public stop 继续停止其获得锁时的当前代。

## 验收

使用真实 Python 3.6.8 / Tornado 6.0.2 的独立有界进程、合成应用、127.0.0.1 随机端口。覆盖原 import 栅栏超时、未建 loop 的 stop、loop 构造前后取消、应用和 listen 中取消、正常健康请求/启停、同实例重启、并发 start/stop 与清理结束无活线程。恢复交错覆盖旧恢复停在停止前、停止后重启前，其他调用者切到新代已就绪、尚未就绪和已退出三种状态；旧恢复全部报告代次变化，新代保持原有取消状态，且不会产生第三代。记录输入 SHA256、退出码和实际观察。

本实验验证生命周期取消语义；现场 SSL 构造/GIL 阻塞首因和生产接入继续待验。候选不改变 HTTP 鉴权、业务 handler、SDK 或原异步 drain。共享规格索引由父任务集成者登记。
