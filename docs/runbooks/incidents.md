# 故障处理规范

类型：长期规范兼响应流程。适用范围：开发缺陷记录与复盘，以及服务不可用、数据错误、交易阻断、状态不明、性能或容量故障的响应。

## 开发缺陷记录与检索

普通、低风险缺陷按[实际影响选择维护量](../development/documentation.md#按影响选择维护量)，可检索的已有提交、PR 或交付结果可承载根因与回归入口。详细事件字段和独立复盘按影响、风险或交接需要采用。

每个开发中发现的缺陷保留可检索记录，可写在已有任务或缺陷单中，以条目编号或链接提供稳定引用，按模块、症状、错误或契约关键词关联。发现时记录现象、预期行为、触发条件、输入与代码身份、影响及处理状态；修复后补充根因证据、修改和验证链接。证据不足时保留假设及待核实条件。普通缺陷采用轻量条目，重大或重复缺陷使用[故障记录模板](../incidents/TEMPLATE.md)单独复盘并加入[故障索引](../incidents/README.md)。

开发相关模块前，检索故障索引及关联规格、任务中的历史缺陷，核对既有预防措施与当前输入是否适用。调查同时检查设计约束、输入校验、测试和监控为何未发现或阻止问题，并沿相同失效模式检查其他入口及调用者。事实、促成条件和待核实判断分别记录，预防措施落实到负责相应行为的模块或流程。

修复项以对应验证为关闭依据；后续预防事项独立跟踪所有者、优先级、状态和可验证的完成条件。通用经验回写所属唯一正文，缺陷记录保留事件证据和链接。参考 [Google SRE 复盘指南](https://sre.google/workbook/postmortem-culture/)的系统改进、可追踪行动和可衡量结果要求（核对日期：2026-11-07）。

## 分级与止损

| 等级 | 判定依据 | 首要行动 |
|---|---|---|
| 严重 | 账户/权限错误、重复副作用、关键事实丢失或范围不明 | 停止受影响新增准入，保留回报和审计，通知运行责任人 |
| 主要 | 核心能力不可用且具有明确影响范围 | 隔离故障范围，执行已验证降级或恢复 |
| 一般 | 非关键能力降级、明确可容忍的延迟 | 保持可观测，安排修复并跟踪恢复 |

分级依据实际影响及服务目标；具体响应时限、联系人和通知渠道由受控运行值班配置定义。

## 调查顺序

1. 记录首次发现时间、环境、版本、用户症状、影响范围和当前保护动作。
2. 保存最小必要的原始证据：关联 ID、状态/事件水位、错误、资源和实际加载身份；脱敏后归档。
3. 沿用户入口、调用链、依赖、数据源和事实所有者定位，区分根故障与关联症状。先核对近期变更和已知恢复条件。
4. 对有副作用的操作核查实际执行结果，保留原命令与未知状态；按授权处理账户操作及数据修正。
5. 在责任层形成修复，复现原条件并验证相关调用链，记录触发链、状态变化和恢复依据。

故障期间保持单一协调记录。重启、切流、重试和清理使用已验证边界及停止条件；保留账本和证据，避免反复操作掩盖根因或扩大副作用。

## 恢复与关闭

恢复检查覆盖：实际部署身份、依赖与资源、数据新鲜度/完整性、未完成工作、未知提交、事件覆盖、权限和活动入口。先只读核实，再分阶段恢复新增准入。

从真实用户入口验证正常、空、异常与恢复场景；观察约定窗口。告警消失和进程健康属于中间证据，故障关闭需有对应业务恢复依据。

阻断核心流程的失败应在进入等待、清理或退出前持久记录 ERROR。保留故障阶段、固定原因及错误码、关联身份、影响、经脱敏的判定现场值和后续处置。短暂失败由事实所有者按原预算重试，记录首次阻断、原因变化及恢复结果。涉及未知外部效果时，沿原请求身份核查与确认，保留原回报和账本。

## 复盘

按[开发缺陷记录与检索](#开发缺陷记录与检索)记录直接触发、根因、促成条件、影响、保护与检测缺口、修复与回归、恢复时间及长期预防动作。事件时间线保存在故障记录。

使用[故障记录模板](../incidents/TEMPLATE.md)，加入[故障索引](../incidents/README.md)，链接代码、发布及验证证据。
