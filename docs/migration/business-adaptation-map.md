# 观衡业务与 WonderTrader 职责映射

类型：迁移实施设计。状态：in-progress。最终产品范围见[系统目标](../product/brief.md)，能力依据为固定上游的[原生能力目录](../development/wondertrader-capabilities.md)。具体源码清单及旧路由历史见[功能清单](business-feature-inventory.md)，实现与运行资格由[当前事实](../roadmap/CURRENT.md)及各项证据登记。

## 职责原则

观衡源码、构建、安装、验证和发行归本仓库。旧QMT工程仅作静态只读来源；券商QMT终端继续作为外部接入端。观衡业务应用与WT原生包独立构建发布，接口及兼容关系显式登记。

WT已有的行情存储、周期处理、策略调度、理论持仓、组合目标、执行器、资金/损益统计及基础订单成交记录直接复用。仅为来源协议、策略特有算法、配置和用户展示增加适配。旧服务数量、SQL表和消息链不构成继续迁入的要求。

当前范围不新增资本拨付、独立资本归属账本、人工持仓归属服务或逐单人工风险审批工作流。策略预算是明确配置，账户实际资金由券商查询，策略理论状态和损益由WT上下文维护。配置预算、数量倍率和组合统计不能解释为券商子账户隔离。

Grafana、新闻及研究功能整体退出，按[ADR-0004](../architecture/adr/0004-core-trading-product-scope.md)执行；独立市场观察及策略必需辅助事实保持明确来源与边界。

## 行情链

QMT来源经标准Parser/源适配进入WT原生行情处理与DSB/DMB；已下载分钟按公开Helper导入，策略沿原Reader读取，独立图表沿已验接口消费。数据格式存在、返回条数、真实覆盖、单位精度与可执行资格分别证明。

原生Servo/Reader的缓存与切片所有权、派生周期更新和分钟形成/闭合限制按[原生行情接入收敛](native-market-integration-plan.md)及[能力目录](../development/wondertrader-capabilities.md)处理。源缺口只补来源与必要质量边界，不恢复全量PG分钟副本或复制原生周期算法。

QMT分钟下载下界为2021-11-01。范围、上市日期、休市/停牌/无成交和确实缺数分别核实；不能按文件存在或零量猜测完整性。当前真实来源验收使用QMT，TDX仅保留可选适配，现场对照暂停。

## 策略、资金与执行链

完整历史/辅助及配置→共用策略规则→原生上下文/目标→已配置原生风控与执行单元→QMT Trader适配→原策略线程调用→查询/回报返回原TraderAdapter。回测使用WT回放/撮合；策略实际运行和模拟数据分别标识。

策略特有信号状态由明确算法重建或映射，通用理论持仓、目标、执行差量及盈亏采用WT。预算配置参与数量计算，不新增资本归属服务。接口鉴权、账户许可、风险规则、人工操作授权和委托结果分别表达，人工开发/发布审批不构成应用逐单审批流程。

原生查询与push并非默认共同柜台事务；按具体插件核对来源、顺序和快照回报交接。WT既有日志优先使用；只有明确的源端未知提交或可靠请求去重缺口才补最小身份事实，不以旧多账本相等作交易前置。结果未知保留原委托/请求身份，核查后再决定后续动作。

## 接入与部署

共享内存源端已完成真实行情读取验证，用户已允许WT接入，按[QSW](../specs/qmt-shm-wt-binding.md)在本仓库独立Host/Agent和C++ Parser/Trader适配。终端HTTP仅保留临时流程历史证据，停止后续优化和部署。终端外Host的签名HTTP与终端内共享内存分工明确，不做旧终端HTTP回退。

初期只开放已验证的market.full_tick；历史、账户、分钟订阅、委托与撤单逐项接入并验收。受限Agent遵守Python3.6、原策略线程调用及无普通文件/网络职责。原生共享内存广播WT-D10与QMT认证消息协议不同，按真实协议接入。

新Host只读Journal保留必要通信请求身份/派发/终态，使用终端外内嵌SQLite，不是订单/持仓/资金的另一套数据库，不需要数据库服务。其他数据库只有在具体事实、并发与恢复需求论证成立后选用；若确需部署，遵守Windows原生要求。当前运行数据库、私有资料和旧服务保持，不授权删除或生产切换。

国信终端的[日常操作](../runbooks/guosen-qmt-operations.md)、[维护](../runbooks/guosen-qmt-maintenance.md)、[排障](../runbooks/guosen-qmt-troubleshooting.md)由本仓库维护；新工具及实际加载身份分别验收。

## 交付顺序与限制

1. 完成独立安装及原生行情到策略/图表读取，核真实来源和覆盖。
2. 完整迁入保留的策略算法/版本，同核贯通原生回测与实时上下文。
3. 完成共享内存Host/Agent→C++插件实际链，先只读，再分别验账户、回报及授权写入。
4. 配置、账户、策略、委托、回测和必要运维入口逐项正常/空/错误/恢复验收。
5. 最后形成具体版本、配置兼容、旧活动入口收束、未决操作核查及回退的受管切换。

原生框架新修改先提交必要性、替代方案、范围及证据，取得用户批准再实施。真实交易、终端重启、生产切换及数据删除按具体授权执行。局部模块、模拟来源或独立审查通过，只授对应范围；完整完成条件仍覆盖保留的整体系统。
