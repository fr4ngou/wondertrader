# 券商查询同步到 WT 原生订单表

类型：本次实施提案。状态：accepted。用户已于2026-10-27明确批准按本方案修改两个框架文件；实现与验证进行中。范围：固定上游08b230dd05facf6d650d949bfe51054115a2ecb1及已批准覆盖上的订单查询模式。

## 用户可见结果

券商查询返回本通道的活动订单后，WT自己的getOrders和cancel(localid)使用同一个原生订单表。订单剩余数量以券商完整查询为准，重复查询和迟到成交回报不会再把80扣成60。实际持仓继续使用已批准的position_by_query，整个流程不新增持仓或订单账本。

## 已核实的根因与原生接缝

复用[WT-T01/T02/T07/T09](../development/wondertrader-capabilities.md)的原查询、订单对象、撤单、频率与总量限制。固定源码TraderAdapter::onRspOrders会将本通道活动订单写入私有_orders；cancel(localid)从该表取订单再走doCancel及原频率记录。

批准前的自有[BrokerQueryContext](../../src/GuanhengExecution/BrokerQueryContext.cpp)仅在AS_POSITION_QRYED时转交查询，后续仅更新rows_投影，导致两处订单可见性分离。直接反复调用原onRspOrders会重复累计订单统计；原onPushTrade还会递减未成交量，已查询余量后迟到成交仍可能再扣。该缺口属于本次查询优先接线，不能据此泛化为WT原设计不可用。

已核公开接缝：SPI回调可调用，但私有_orders、_undone_qty和统计表没有仅同步完整订单查询的公共写入接口。把查询伪装成推送会额外触发推送统计、策略通知及查询，不能承担完整快照替换。此前新增受保护撤单入口提案停止推进；本提案优先将订单状态收敛到WT原表。

## 已批准修改范围

用户已批准以下两个框架文件；本次仅按该范围实施：

- src/WtCore/TraderAdapter.h：保存由配置冻结的查询模式及必要私有辅助声明；公共虚接口和cancel签名保持。
- src/WtCore/TraderAdapter.cpp：初始化选择、完整订单查询发布、查询模式下未成交量更新与订单回报处理、订单读取的证券匹配。

自有BrokerQueryContext同步删除独立rows_订单投影和相应数量求和，完整O一律交给原Adapter，由原getOrders/getUndoneQty/cancel承担订单状态读取与撤单；自有提交防重组继续只负责未知命令及防重复提交，不保存金融余额。

## 配置与路径

沿用同一配置order_context，缺省及native走原路径，query_first显式启用本提案。query_first要求position_by_query、来源完整ORDER批、固定owner线程发布和有界max_rows。非法值或条件缺失在初始化失败；运行时不热切。配置不自动开启交易权限或真实写入。

## 新路径的具体行为

1. 完整成功的订单查询在owner准备候选，再发布到WT现有活动订单表与未完成数量；活动订单按WT原通道身份归属，外部手工单不伪造localid。已终态订单从活动表退出，数量直接取本次查询的剩余值。
2. 订单查询原有统计字段按本次完整订单列表刷新，不把同一整批再次累加；成交统计字段与原频率时间缓存保留其原职责。查询后缺少某行只能表示本次没有观察到，不能据此把未知提交解释为已撤或已成交；插件原未决命令继续保留并禁止自动重发。
3. 查询模式中的增量updateUndone不再自行调整查询余量。订单/成交回报继续原策略通知、成交统计、日志、账户查询及持仓刷新，并触发后继ORDER查询；订单推送不覆盖已选择的查询订单状态或重复累加订单查询统计。
4. cancel/doCancel继续原生实现和风控。券商查到本通道活动订单后，原生cancel直接从原表取得其原EntrustID/OrderID，交原ITraderApi.orderAction；不增加撤单旁路。
5. 原getOrders在查询模式按规范证券身份匹配原表；默认native的匹配与原行为保持。无活动单返回空表；当前查询未就绪、断连及未知提交的新写控制继续由既有Standard/宿主准入承担。
6. 首次登录原P/O/D/A推进顺序保持；重复ORDER刷新只更新订单观察，不重复驱动整条初始化。查询失败不发布成功空表。查询和回报均在交易owner，网络仍在现有I/O worker，SPI外释放自有锁；跨策略线程交接继续由宿主的有界队列负责。
