# WT 私有持久化迁移与写入排查

状态为分阶段实施，当前覆盖正式 WT、QMT 通信、分账及观衡相关读取链。长期开发规则与持久化合同见[统一规格](../specs/wt-private-persistence.md)。

## 首轮实施证据

- 分账按柜台业务状态和来源类型比较。交易日、成交或委托身份、经济字段、归属以及费用有变化时进入原归属校验。查询传输字段变化复用原收件。测试覆盖重启后重复成交、后到费用、经济冲突，以及已入账卖单恢复内存冻结状态。
- 通过 `python -B scripts/wt_allocation_compact.py <源分账库> <新演练目录>` 制作原库的一致性备份、归并候选和旧收件序号映射。`verified.json` 只在候选通过完整性、逐表对账和收件数量校验后生成。启动正式实例前继续使用原切换流程。
- 2026-11-14 正式账本只读备份演练中，收件由 93,007 降至 262，数据库由 137,924,608 字节降至 8,220,672 字节。92,745 条旧收件映射回候选代表，原库副本保留其正文。账户身份、账本主记录、业务明细、事件、来源证明和冲突六表双向对账一致。此步骤保留全部既有来源证明。
- 同一候选账本分别在 D/E 盘追加 1 千、1 万和 10 万条历史收件，固定每批 61 条重复事实，各跑 120 批收件。D 盘 p99 分别约 2.22、1.80、2.47 ms，E 盘约 3.30、3.19、3.24 ms。六组均零新增重复收件、WAL 文件零增长。本项覆盖分账收件调用，真实成交投影、QMT 往返和物理写入量另验。
- 混合压测从原归属回调入口提交 60 条重复回报和 1 笔新成交，每组 100 批，三种历史量为 1 千、1 万、10 万条。D 盘 p99 为 15.78、12.07、17.87 ms，E 盘为 221.39、441.80、321.99 ms。每组核实 100 笔新成交及零重复收件。覆盖本地回调、归属投影及 WAL 提交，QMT 往返与物理写入量另验。10 万条历史下，已提交内存视图取样 1 万次，p99 为 5.1 微秒。
- WT 父状态保留初始和最终同步发布。常态通过一个后台线程原子替换，等待槽只保存最新一份。相同正文按一秒心跳刷新，供观衡显示发布时间。回归覆盖后台写入阻塞时的覆盖合并、Windows 共享冲突、首错诊断及严格 ready 收据。

## 跨盘候选准备与策略状态

- 通过已安装运行时执行 `python -B scripts/wt_private_storage_prepare.py --service-config <当前服务配置> --private-root <D 盘独占新目录>`。入口在原 CURRENT 服务租约内核对 WT 已正常退出，并核原生 ready、closed、干净关闭标记和实际进程退出。复制期间同时持有源原生目录和 QMT 通信库的写入租约。候选目录包含 Native 恢复与历史输出、QMT 通信库和策略分账库，数据库使用 SQLite 一致性备份。关闭后有未合并的 WAL、文件篡改或重用既有候选目录时，材料准备或复核会失败。
- 准备入口为 QMT 制作完整备份，并将归并候选、分账原库及原收件映射的校验摘要绑定到同一停机水位。候选 Native 配置的 `private_storage_origin` 引用该材料，`output_directory` 与 `shared_account_storage.allocation_root` 选择已核候选。用原交易 Host 解释器执行 `python -I -B scripts/wt_private_storage_pair.py --pair <原配对> --output <E 盘新配对目录> --journal <候选通信库>` 生成后继配对。离线实测新旧 QMT 配置除通信库和材料路径外相同，策略正文和交易规则逐字一致。以同一 CURRENT 和服务控制根调用 `adopt-private-storage --storage-receipt <收据> --storage-sha256 <摘要> --service-config <后继配置>`。Python 核两库及原服务身份，Native 在两根租约下复核停机状态并归档旧根的关闭标记。控制根和日志路径迁移、真实不下单演练与回退验证另行完成。
- 用 `scripts/wt_private_storage_successor.py` 从已核停机收据、已生成的 QMT 配对和固定 Native 模板生成候选服务配置。参数为 `--service-config`、`--storage-receipt`、`--storage-sha256`、`--pair`、`--native-template`、`--native-sha256` 和 `--output`。候选执行代的控制收据、策略投影和执行日志写入私有根下的 `execution-control`。第一次接续按原观察引用读取 E 盘收据，后续重启按新引用读取 D 盘收据。工具保留同一公开 CURRENT、服务租约及原解释器入口，生成候选后执行与正式采用相同的库和绑定检查。
- `--no-order` 使用原权限交接协议将候选 `trader.writes_enabled` 置为 `false`，冻结前代配置的路径与摘要。候选执行描述符与 Native 模板绑定同一安装根。正式前代的两策略配置通过 Python 和原生兼容检查，篡改账户或前代摘要均被拒绝。实际服务启动、两策略计算和柜台只读核对继续验收。该准备工具仍沿正常关闭收据准入。
- QMT Host 换安装时，用候选 Host 的 `python.exe -I -B` 执行配对工具，并用 `--origin-python` 指定原 Host 的 `python.exe`。原解释器核旧配对，候选解释器生成并复核新配对。后继服务从新配对清单取 Host 解释器及 Agent 路径，可另用 `--successor-pythonw` 选择候选 WT 解释器。实测候选 Host 使用 D 盘通信库副本，配对策略正文与操作权限文件的摘要一致。权限切换同时更新 Native 安装引用时，前后依赖材料只允许当前安装项变化，合约、费率和过滤规则摘要仍逐项核对。
- 独立候选安装已用正式配置核对 16 项原生安装文件和 298 项 Python 绑定文件。正式两套策略在换原生安装且关闭写入的情况下，Python 和原生均通过兼容检查，篡改依赖或账户均被拒绝。受控候选目录 `wt-private-persistence-python-candidate-20261114` 的两份收据分别记录安装验证和兼容验证，真实柜台调用为零。
- 后继父进程和交易 Host 分别使用私有根下的 `runtime-control` 和 `trade-control`。父进程继续使用原实例锁，同一逻辑实例的 E/D 入口竞争同一把锁。交易 Host 用现有受保护的 Windows 目录权限创建新代，在 D 盘读回启动、退出、首错及请求失败回执。发布需装入本次 WT 与 QMT Host 的候选程序，原配对保留原安装路径约定。
- 受管进程的后台日志写入者合并队中同一来源的连续普通记录，启动、异常和退出单独同步，文件格式、记录顺序和轮转容量沿原约定。阻塞首笔同步再放行的回归中，20 条普通记录和 3 条关键记录合计同步 4 次，全部按原顺序读回。启动记录在退出前被轮转时，恢复入口沿既有备份核对同一控制代的启动记录。
- 原生 CTA 的普通日志先入有界内存队列，后台约每 100 毫秒合并刷新，正常退出排空。警告和错误在原调用处写入并刷新。日志状态发布队满丢弃数和主动刷新数。D 盘探针用原 WT 日志入口发送 100 条普通记录，顺序一致、零丢弃、共请求刷新 2 次（含退出刷新）。另通过四文件轮转、UTF-8 截断、文件打开失败、轮转共享冲突后恢复及错误关闭前可读。刷新计数衡量日志器调用，物理写入字节和突然断电后的保留范围仍需实测。
- 两套线上策略通过 `StrategyStateRecord` 沿原用户变量读取版本、提交一组业务字段并拒绝过期版本。各自保留原 JSON 布局、阶段、周期、信号消费水位及 ATR 保护线。只有回调观察序号变化时跳过写入，实际阶段、周期或换代身份变化仍保存。原生回测也使用同一版本化接口，沿每次回测独立的 WT 用户变量保留原格式。实盘用户变量仍沿原 Native 保存时点，目标与自定义状态的掉电一致性、通用原生状态按变化保存继续实施。
- 服务切换回归覆盖错误凭据时拒绝启动、采用候选后按同一配置正常重启，以及原账不变。原生跨盘回归用 Python 生成迁移收据，C++ 实际认领正常和中断后续跑的候选，验证新旧金融文件摘要一致。已撤回、原账已变或已认领的候选均被原生准入拒绝。原生构建和八项券商替身执行回归通过，真实柜台调用为零。正式配置下两个策略的整链不下单演练仍待完成。

## 撤回尚未接管的候选

执行 `python -B scripts/wt_private_storage_prepare.py --service-config <服务配置> --abandon-receipt <迁移收据> --storage-sha256 <摘要>`。候选尚未启动时用原配置，候选发布 CURRENT 后在接账前退出时用候选配置，沿代际记录核原停机水位。入口保持原服务租约及新旧原生目录和 QMT 通信库的写入租约。QMT 候选仅有只读查询变化时逐表核对其余通信事实，策略分账及原生文件继续核原停机摘要。先持久化撤回，再恢复已归档的旧关闭凭据及旧 CURRENT。中断可用同一收据续做。撤回后沿原普通启动入口启动。候选已认领或已有新增交易事实时，保留候选及原件，转入反向对账流程。

## 策略决策与重启

旧版实盘回调先经归属桥提交目标，再更新 WT 内存中的用户变量，计划和模型状态可能在账本目标之后才落盘。正式 `677827d8` 已将两套策略接入[账本提交边界](../specs/wt-private-persistence.md#persist-03-策略如何保存自己的数据)。归属桥在报价和完整目标预验后、原生 setter 前，将状态和目标写入同一事务。重启分别核账本目标、原生结果和已有委托。

使用正式 `677827d8` 的已安装运行包及 D 盘正式账本的一致性副本，让独立进程分别在 SQLite 提交前与提交后立即退出。两份副本均通过 SQLite 完整性检查。提交前恢复原状态与目标，候选目标事件不存在。提交后恢复新版状态和目标，同时读回原目标身份。该测试覆盖账本提交边界和原身份读回。两套策略回调的行为见本地 CI 和正式不下单验收。受控收据为 `strategy-decision-crash-677827d8/RESULT.json`。

分账恢复回归覆盖三种进程直接退出时点。提交前退出时，后继取得原输出租约，读到原收件并应用一次成交。提交后立即退出及完成 WAL 合并后退出时，后继读回已提交结果，重复成交不再入账。另在成交事务未提交时通过独立连接运行 SQLite 的被动合并，验证策略仍读取上一份已提交快照，提交后才能读到新持仓。这些验证使用合成成交和独立账本。

## 通用原生状态按变化保存的修改范围

正式失败分钟线已用同一 Reader 和基础资料回读。沪深 300 ETF 在 11 月 14 日 18:08 的请求，从正式归档及 D 盘副本均读到 11 月 13 日 15:00 的一根闭合分钟线，首次读约 1–6 毫秒。两套策略在原启动截止内只对暂不可用返回码复读主分钟线，其他原生错误沿原方式退出。18:49 正式恢复通过，原生故障时瞬时返回空的内部原因尚待复现。

原生策略接口可更新策略自定义用户变量。它通过原 dirty 标记影响部分保存调用，无法接管上下文私有 `save_data`、`save_userdata` 或引擎内部 `save_datas`。这三个保存点分别写策略金融状态、用户变量和组合资金持仓文件。公开回调和插件能处理自己的状态，原序列化文件仍会按引擎原时点写入。外部事后去重仍承担首次写入开销，也无法与原文件失败边界合并。

按变化保存拟只在受管 CTA 的原保存边界实施。`CtaProcess.cpp` 负责校验并绑定 `native_state_save`，`CtaStraBaseCtx.cpp` 和 `WtEngine.cpp` 复用原序列化字节，在显式 `on_change` 时比较本代已成功提交的摘要与文件身份，内容变化或文件已更换时原子发布。缺省与显式 `native` 沿原调用。保持策略回调 ABI、JSON 布局和调度时点，补丁只涉及受管接线及上述保存点。升级时重新核对三个原写入边界及对回测和其他引擎的影响。回退用原模式和同一原生文件格式，保留原关闭及账本交接。

验收比较缺省、显式原生、按变化和非法配置，观察同状态重复调度、单字段变化、文件缺失、发布中断、重启回读和现有回测。三个文件各自的原子替换无法证明它们与目标委托一起提交，后者仍需单独核验。上游源码修改需按[上游规范](../development/upstream.md#日常修改)明确批准，当前保持上述原生保存点原样。

## 实施和迁移顺序

部署配置分别指定原生金融根、QMT 通信库、分账目录、运行控制目录和日志目录。目标以已配置的 D 盘私有根为共同父级，各模块在其下独占自己的目录。稳定入口继续引用新控制代，历史控制回执与金融档案的既有引用继续可核对。账本归并和迁盘分别生成验收证据，避免在一次比较里混入两种变化。

1. **基线与离线演练。** 固定源码、安装、运行配置和原数据水位。用 SQLite 一致性备份保留通信库和分账库，另保留原生组合、策略、用户状态、历史输出、恢复收据、当前指针及文件摘要。副本用独立租约和写入禁止的执行配置。在相同输入上分别跑旧版、仅去重及仅迁 D 的对照。
2. **先去重，再压缩副本。** 加入业务身份及状态索引。逐行校验原正文摘要，确定性合并重复回报，保留最早合格的原回报、补齐字段、独立证明和冲突。保留可重放的未归属事实、原顺序和水位映射。验证后用 SQLite 生成压缩副本，保存原库作为只读迁移档案。比较表、策略账、命令、冲突、待处理事实和原证据可达性。
3. **接入 D 盘和内存发布。** 先接入快照后台发布及一个现有策略的恢复状态，再接入其余策略。现有通信交接要求同一 journal 路径，原生恢复也校验旧配置与状态根。新增受控迁移交接材料，固定前后路径、账本和部署身份、文件摘要、原进程退出证明、交易水位和已核快照。Python 服务交接及原生恢复准入均需核对该材料，普通重启继续使用同路径检查。原生历史输出按原目录结构接续，旧控制目录保留供引用和审计。
4. **正式切换及验收。** 正常停止原 owner 并核实所有写入者退出，记录待确认提交、活动单和最后回报水位，以停机后的版本重新制作备份并执行迁移，原目录保留。用新配置在 D 盘获取唯一租约，先运行不下单验收，逐项核查原资金、持仓、已知活动委托、未知责任、策略状态、WT/观衡读取和首错日志。发布启用沿[发布手册](../runbooks/release.md)。
5. **回退。** 新库没有接收业务变更时，确认新 owner 已退出后可沿原配置和原账恢复。新库已经接收新回报或委托时，先核对增量、未知提交与柜台事实，通过已验证的反向迁移接续。旧库水位落后时停止新增委托并继续核查。验收通过后撤下旧活动写入口，原档案按既有保留约定管理。
