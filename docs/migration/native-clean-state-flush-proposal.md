# 原生最终保存接口候选（必要性待验证）

类型：核心接口候选研究。状态：proposed，必要性待验证，已撤回当前审批请求；相关WT源码保持只读。日期：2026-10-28。关联：[STQ-P19](../specs/native-qmt-standard-trader.md#stq-p19-受管多策略产品宿主与干净停止恢复accepted开发中)。

## 现有能力与必要性核验

受管多策略宿主复用WT已有策略状态、主动登记的用户KV和组合文件恢复运行，恢复准入核对未决交易责任及关闭结果。持仓、费用和绩效继续由原生记账；当前任务没有新增“每次停止必须强制重写所有状态”的要求。

WT已经按原业务事件保存并加载策略理论状态、主动登记的用户KV和组合账目。若本轮内存值与已保存文件一致，再写一次属于重复写入。当前尚未通过正式策略停止/恢复主链证明存在影响恢复的未保存更新，也未证明新增公开入口是必要方案，因此先使用和验证原生保存/加载机制。

2026-10-29已用固定原WT库直接加载既有产品正常停止文件的副本，读回A800/B400、组合1200及两策略用户KV，无额外保存；原件及副本金融JSON摘要保持。[实际证据与边界](../evidence/2026-10-29-configured-bt-and-native-load.md)支持继续复用已有机制，产品同根两代及交易责任准入仍需完成。

这里讨论的内容限于原生已有的持久状态：策略理论持仓及开仓明细、累计盈亏/费用、待执行信号和条件单，以及策略主动通过用户数据接口登记的键值。策略函数的临时变量和Python任意内存对象不在保存范围。新增入口没有提出新的业务数据种类。只有明确要求恢复的某项值在现有保存事件后发生变化、停止后确实丢失且影响正式策略恢复时，才有进一步研究的依据；本轮尚无此类证据。

源码事实是：`CtaStraBaseCtx::save_data/save_userdata`为私有接口，`WtEngine::save_datas`为受保护接口；`WtCtaEngine::stop`及自有Session关闭没有汇总保存结果。原函数忽略创建/写入失败的结果。这些事实说明候选接口与现有能力的区别，不能单独证明当前业务必须扩展核心。先核原生停止/恢复的实际结果，再定位具体缺失字段、最后修改事件、已有保存事件及实际影响。

原on_init示例已纠正：正常启动中，随后base session_begin会保存on_init登记的dirty KV。源码提示的待验证边界为策略on_session_begin在base保存之后修改KV、之后无后续保存事件即停止；此边界尚无本轮实际运行证明。普通调度结束也会保存dirty KV，设置新信号会立即保存，不能笼统声称末次调度未保存。

## 现有接缝和替代方案

- 原`load_data/load_userdata/load_datas`承接恢复；现有JSON结构和原序列化是唯一金融状态来源。
- 读取并哈希既有JSON只能识别文件身份，缺少最后一次内存修改已保存的证明。
- `getFundInfo()`会调用组合保存，但没有写成功结果，也不覆盖各策略私有KV。
- 人为触发行情/交易日结束回调会引入业务事件；后继核验直接使用真实原生保存/加载流程，是否需要额外最终保存入口由实际缺失状态及业务影响决定。
- 自有模块复制原序列化或维护第二份仓位/KV账本会重复原生职责，当前选择继续使用原保存实现。

## 历史候选范围（必要性成立后另行审阅）

| 文件 | 拟议改动 |
|---|---|
| `src/WtCore/CtaStraBaseCtx.h/.cpp` | 增加显式公开保存入口，复用同一`save_data/save_userdata`序列化；内部保存返回创建/写入是否成功，公开入口汇总结果，不生成调度/成交/交易日回调 |
| `src/WtCore/WtEngine.h/.cpp` | 增加显式组合状态保存入口，复用`save_datas`并返回保存结果；保留原字段、路径和收益计算 |

接口只在外层已停止准入、Parser/Reader停止、ticker/pool/tasks已join之后由同一owner调用；成功需要全部原写入成功，自有生命周期元数据再绑定这些原文件摘要。保存失败保持恢复未就绪。

此前fresh/resume_clean候选描述存在首代如何生成恢复证明的缺口，当时撤回该配置设计的实施请求。原生加载方式与未来是否增加显式最终保存能力需要分别说明，不能靠新接口或三个JSON文件证明活动订单、未知提交等全实例交易责任已经结束。后继[P21产品候选](../evidence/2026-10-29-native-clean-recovery.md)沿原业务保存/原init加载及全实例责任准入，实现显式原生record_clean/resume_clean成功关闭后的recovery_ready=true；fresh及未获准入的profile保持false。新代在原文件写入前消费旧clean证明。该后继没有实施本保存接口提案，完整恢复资格仍在逐项验证。

## 风险、验证与回退

风险是核心接口/签名和所有消费者重编、关闭期数据一致性、写失败的结果传播及上游维护。该提案不承诺断电持久性；异常退出/未知命令恢复仍沿原Host/Journal和命令身份核查。原生头、库和插件必须绑定同一构建身份。

验证先沿原生机制跑安装后停止/恢复主链：A/B原JSON、用户KV和组合目标恢复，券商已满足目标时不重复提交。核on_init写KV经session_begin正常保存的基线，再验证前述session_begin末次KV边界是否影响实际需求。若发现真实缺口，保留原触发条件、内存/文件具体差异、替代方案及业务影响，重新审阅必要性。创建/写入失败、部分文件失败、未决命令/活动单、损坏/配置变更及pending关闭分别记录。核心候选扩展尚未获得实施授权。

回退到当前已核定核心和自有Session的已有根拒绝行为，保留所有原状态及Host/Journal，不删除文件、不切新空根重发。仅接口扩展批准后实施这四份核心文件；真实下撤单及生产切换仍按另外授权处理。
