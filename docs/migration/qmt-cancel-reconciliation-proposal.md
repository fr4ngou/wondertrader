# QMT撤单异常与跨日旧单同步方案

类型：方案。状态：实施中，2026-11-06；用户要求在独立worktree修改。撤单后复查及有未结委托时周期O/P/A源码与隔离验证已完成；历史委托接入、完整组件联调及发布尚待完成。

## 目标与已核事实

旧委托随后撤销、废单、成交或跨日退出后，WT订单表、执行器监控、未成交量、策略pending及券商持仓/资金能够收敛到真实结果。

按[WT能力目录](../development/wondertrader-capabilities.md)的WT-T02/T03，复用原ITraderApi/ITraderSpi、TraderAdapter订单表、股票执行器、订单查询及持仓/资金查询。当前安装的WT DLL已隔离验证：新tick到来后原超时监控连续请求撤单，达到原实现的重试处理条件后移除监控；原订单未成交数量仍需券商观察更新。该事实不能解释为券商已撤单，亦不构成修改WT框架的依据。

当前QMT适配器的正常order/deal回报会触发原查询；orderError沿原错误通知但尚未触发订单复查。既有周期刷新主要覆盖资金和持仓。已知订单次日从当前查询范围消失的含义，需要结合查询覆盖日期及原单事实核实。既有[恢复规格](../specs/execution-fault-recovery.md)和[事件规格](../specs/native-qmt-standard-events.md)继续适用。

## 根因与职责

撤单发送成功、撤单拒绝与原订单终态分别是不同事实。当前接入缺少从撤单异常回到原订单查询的接线。WT负责超时、重试、拆单和差量执行；QMT插件负责把终端实际订单及账户事实映射给WT。原Identity、命令journal和券商单号继续承担关联，不另建订单状态机。

## 建议修改

1. 撤单调用完成、收到撤单相关错误或连接恢复时，通过现有交易owner安排一次订单核查。错误正文只作为查询触发，原单身份仍由原命令、券商单号及实际交易日期核实；无法定位的业务错误触发原完整订单查询，不能按错误文字猜测终态。
2. 有已知活动单或尚待核清的原委托时，在既有刷新节奏中加入订单查询，正常现场沿当前30秒配置。查询在现有队列和线程执行，合并重复触发；在途查询先结清，后到触发不能被更早的查询结果冒充覆盖。
3. 查询得到原单的明确状态后，沿现有WT回调/订单表同步；终态之后刷新持仓和资金。部分成交只采用券商实际成交及持仓结果。核实原执行器监控及策略pending同时完成交接，不能仅清监控或仅清表。
4. 当前订单查询缺少原单时，核来源交易日及实际覆盖范围，优先从QMT提供的原日期委托/成交接口查该笔原单。空结果、资金解冻或撤单报“订单不存在”单独出现均不足以证明具体终态。接口暂时不可用时保留原身份和待核实状态，后续原查询继续；查询失败沿既有读取恢复，不新增全系统停机或上线审批。
5. 正常撤单回报、查询核实、重复及迟到回报统一进入现有金融观察链。相同原单重复观察不会再次计算成交、重复扣资金或重复发单。WT原有超时和重试策略保持，改动优先限定在自有适配层。

## 实施前必须核实

- 国信QMT当前版本的历史委托/成交查询能力、日期参数、保留范围及返回原单身份；现有四查询接口不能被直接宣称具有未验证的历史范围。
- 跨日仍返回旧活动行、当前查询不含旧单、返回明确已撤/废单三种来源事实分别处理。
- 原查询路径更新WT表后，原执行器监控及NSQ的同单交接实际生效；优先用既有回调，不通过伪造成交或假撤单清理。

官方[内置交易函数](https://dict.thinktrader.net/innerApi/trading_function.html)已列出`get_history_trade_detail_data(accountID,strAccountType,strDatatype,strStratDate,strEndDate)`，支持ORDER/DEAL及显式起止日期，返回按时间分组的结果。该官方定义解决接口查找问题；本机国信版本、模拟柜台的实际结果及当前SHM协议接线仍须独立核实，不能把未调用/不支持转换为空成功。

## 当前实施与验证边界

分支`codex/qmt-cancel-reconciliation-20261106`，工作目录`wondertrader-worktrees/qmt-cancel-reconciliation-20261106`。修改集中于自有StandardQmtTrader：撤单完成或业务错误触发复查，已有活动单/原提交责任时沿现有刷新队列执行O→P→A；在途O之后到达的新触发保留给后继一轮。读取恢复仍沿原四查询，明确拒绝的撤单只通知原WT并触发查询，原订单身份保持。

实际调度函数编译回放已通过普通A/P、活动单O/P/A、重复触发合并、晚到触发、入队失败、原单缺行、读取恢复及持有原读取票据等10个场景；实际error分支通知/触发及SPI异常验证通过。完整StandardQmtTrader翻译单元亦已用原合格工具链编译通过。当前证据属于源码编译及队列/SPI替身，不代表整插件及券商跨日终态已验收。原件位于受控QA的`worktree-audit-20261106-002`。

合入前补执行真实run_write尾部分类→publish_write_failure的14场景：SDK确认未调用、SDK返回signal_sent=false、真正未知、运输失败、身份冲突、原首错、SPI异常及默认路径。SDK返回字节由固定JSON提供，队列与SPI使用替身；没有真实金融调用。独立delta审查通过，合入状态及未覆盖范围见[验证记录](../evidence/2026-11-06-cancel-refresh-integration.md)。

## 验收与发布

先用实际安装组件跑通“旧挂单→撤单异常→原订单查询→明确终态→后继持仓/资金→继续原目标”主链，再集中覆盖以下场景：

| 场景 | 可观察结果 |
|---|---|
| 正常撤单、柜台自动撤单或明确废单 | 原订单退出活动表及监控，未成交量/pending收敛，资金采用后继券商查询 |
| 部分成交后撤单 | 持仓只反映真实成交，后续委托只沿原目标差量计算 |
| 拒绝撤单但原单仍活动 | 原单保持活动，WT继续原超时/重试，查询继续 |
| 跨日当前列表不含旧单 | 按原日期核查，不以空列表伪造已撤；无法核实则保留原责任 |
| 回报缺失、重复、迟到及带挂单重启 | 查询兜底；原命令身份保持，无重复计账或重复提交 |

正式验收记录来源查询覆盖日期、原订单号、状态变化及WT同步结果；30秒是调度间隔，实际发现延迟同时记录QMT响应及排队时间。当前运行实例、原两笔委托及金融数据保持。新增WT框架改动若最终确有必要，另按既有审批规则说明必要性及配置分流；本文不预先授权框架改动。
