## 统一决策建议

### DEC-001 QMT 共享内存绑定

建议先复用原 Python Broker 客户端和受管外部 Runtime。共享内存的认证、布局、代际、许可和 Journal 继续由原工程唯一维护；WT 只消费类型化端点。这个选择能保留已有 Bridge 的审批和签名链，避免另写跨语言协议。直接 C++ 绑定适合后续确有延迟或运维收益时引入，前提是正式冻结 ABI、身份、预算、恢复及实际终端权限回执。

当前可审阅结果是原生 Parser/Trader、运行时调度、Python Broker 门面及隔离调用链。待定范围为二者实际绑定和服务生命周期。上游只读控制 RPC 与 SHM 已有开发实现；实际命令路由、原生启动和交易恢复资格分别等待上游交付。选定绑定方式不会自动授予实盘资格。

执行接入沿原TraderAdapter的四查询、查询与push分工、委托关联及各插件重连方式验证。四次HTTP查询分别保留来源与执行区间，不附加共同柜台事务要求。此前原子四快照/事件水位是旧自有候选的设计条件；是否仍需某项增量保证，由实际回报交接、重复/乱序及未知委托的原生行为决定，先给出具体缺口与证据，再形成适用契约。原生初始化、合计只读和真实执行分别取得资格。

### DEC-002 通达信交易

建议首期使用 QMT 作为执行通道，TDX 提供可选行情/历史；保留 TraderTDX 的同一受管接缝。若业务确需 TDX 执行，后端须提供可核实的接口来源、使用许可、账户查询、委托/成交回报、关联 ID、未知提交核查与恢复依据，再按相同隔离契约接入。

快捷键和界面按键方案需要额外证明输入焦点、请求身份、实际受理与可靠回报，当前没有对应资格证据。当前默认工厂和裸委托会明确拒绝；开发验证中的假端点没有加载用户终端或未知 DLL。

### DEC-003 真实历史来源

已经确认以 QMT 为主、TDX 作为可选来源，QMT 已下载十年历史可以用于补充。导入前仍须固定具体样本、证券、源单位、分钟左右边界、复权/因子及日历停牌规则；这些语义由真实样本和来源所有者验证。原生 DSB 及观衡模型的开发链已经按不同量/额系数核算，来源切换需要新版本，缺少覆盖依据保留 unknown。

本项登记实际数据集的固定 profile 和验收缺项，主数据源选择已成立。真实缓存读取、导出或查询均在获准的外部 Runtime/Host 边界发生，受限 QMT 策略侧继续使用已有内存通信契约。选定 DEC-001 的运行绑定后，开发继续核实实际输入，不能让用户猜测单位或用合成样本推断实际格式。

### DEC-004 观衡业务发布归属

建议观衡服务继续独立受管发布，原生包分发 WT 底座和兼容门面，纯核心以固定版本的受控依赖接入。当前开发验证显式加载原仓库并核对逐文件 SHA，未把私有业务实现分发到 fork。

另一选择是将纯策略/业务契约提取成共享受控包，再由两侧消费。这需要明确包所有者、版本和发行位置。原 Research/Portfolio/Bridge/Console 的实际启用与页面验收仍属于后续服务接线及切换；保留服务和 DTO 兼容测试分别记录，尚未切换线上来源。
