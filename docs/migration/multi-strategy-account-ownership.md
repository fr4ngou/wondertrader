# 同账户多策略的持仓、订单与统一执行

类型：专项评估与实施方案。状态：proposed。日期：2026-10-28。负责人：本对话的交易接入维护者。自有适配沿已授权范围推进；真实下撤单、生产切换及新增WT核心行为须另有明确授权。

## 结论与目标

保留券商查询权威及WT原生策略状态，补齐自有多策略装配。A要600股、B要400股时，WT汇总为账户目标1000股；A退出后目标变400股，执行器结合券商实际仓位与活动订单处理600股差额。策略同时买卖时先合并最终目标，执行净差额。订单属于账户执行通道，实际成交收益与原策略理论收益分别展示。

原生已有三层记录：各策略理论账本、WtEngine净额组合账本、券商通道实际数据。策略独立计算持仓、费用和盈亏，净额组合维护轧差后的理论成交与收益，执行器结合实际持仓和未完成订单推进目标。已实际验证同单买1000、部成500后P500/U500，下一行情没有重复委托；两策略保持600/400。见[核对证据](../evidence/2026-10-28-multi-strategy-reconciliation.md)。收益差额沿三层原记录核对；真实费用及完整金额桥接仍待验，保持自有持仓/分摊/绩效账本新增0。

根因假设已经源码确认：原自有CtaExecutionSession只创建一个CtaStraContext。把它复制为每策略独立Session/执行器，会使各执行器把自己的目标与同一账户总仓比较，形成争抢。正确装配是一组策略进入同一个原引擎，再进入同一个交易owner。

本次无需回退上述已批准查询行为，也无需修改WT核心。原默认native路径及现有批准覆盖由各自证据继续约束。

## 事实所有者与调用链

`策略工厂/参数 → 每策略CtaStraContext → 原WtCtaEngine调度与汇总 → WtExecuterMgr → 唯一OwnerExecCommand → owner pump → 原Local/执行单元 → 原TraderAdapter → Standard → Host/SHM → QMT`。

券商完整查询 → 原Adapter持仓/订单/资金观察 → 同一Local读取实际仓位、可卖量及未成交量。策略仅提出自己的理论目标。共享资金的实际可用量归账户；策略配置预算用于目标计算，预算总和及委托资金约束需在完整业务接线验证。原生理论损益按信号/行情推演，组合净额成交不能直接分派为某策略真实成交收益。

CTA首轮保持poolsize=0，原ticker拥有调度；所有策略计算结束后，原管理器提交完整目标。owner桥按FIFO交付行情/目标，原Standard提交组保留SDK已返回但券商尚未可见的命令责任。相同账户、相同证券同时由第二个进程或外部算法执行仍可能争抢，部署入口须保持单一执行责任。

## 实施步骤与边界

1. 在自有Session增加1..64个策略的固定集合，初始化前检查指针、参数及策略名唯一性；保留单策略入口。构造成功统一接管，构造抛异常时由调用方保留。关闭先停止全部生产者，再逐项通过原factory删除；删除失败保留树且不重复调用。
2. 实际原Factory/Context/ticker/汇总/Local/Adapter/SHM/SDK替身跑通600+400、A退出保留B、反向目标净额与活动订单抵扣。禁止直接手调schedule替代原ticker。
3. 检查重复ID/参数错配、初始化失败、停止与删除失败、已有状态根拒绝、人工订单观察，保留实际证据；独立审查后更新正式规格及入口说明。

集合在启动时固定。停用计算、清仓退出、删除配置具有不同效果：保留目标时继续保留上下文；退出时先将本策略目标归零并确认账户执行与未决责任，再移除配置。直接删掉带仓策略可能触发组合自动归零，当前入口不提供热删。

重启时原WT JSON可恢复策略理论归属，券商总仓无法恢复该归属。现有Session只允许新生成根，继续明确拒绝已有状态根；受管恢复必须另验原策略JSON、原执行目标、未决命令及查询刷新交接，不能换空目录就宣称安全恢复。

手工持仓与人工委托：当前固定集合适用于策略独占管理的标的。相同标的存在额外手工数量时，总目标会影响账户总仓；缺少手工归属信息，自动推断会误卖或回补。保持现有事实，正式接入前明确管理标的与人工操作交接；若要混用，优先显式配置保留目标并走原上下文，实施前确认产品语义。

人工委托还有两个已确认的源码边界：TraderAdapter查询优先发布只把符合本通道原WT标签的活动单加入_orders/_undone_qty，外部订单仅进入来源查询及部分统计；WtMinImpactExeUnit::on_channel_ready会尝试取消已有未监控订单。外部活动单可能与自动执行叠加，本通道历史单也可能触发启动取消。人工活动订单的完整来源观察、执行阻塞/抵扣及取消归属须作为独立适配需求验证，当前禁止据本测试推定混用安全。如需改变原Adapter/算法行为，先提交准确范围及配置选择供用户批准。

## 受管产品宿主与干净恢复实施

2026-10-28后继已交接本对话实施。目标是独立安装后通过显式JSON配置启动固定策略集合，沿原工厂/Session/引擎/执行器/Standard插件运行，并由既有ManagedLocalProcess/ProcessJob监督关闭。原生策略工厂、行情Parser、Reader和基础资料均使用显式安装路径；凭证只通过原环境变量契约传入。读取状态和错误只公布有限生命周期字段。

已确认缺口为：当前仅安装静态库/头，完整宿主仍在测试探针；Session已有根拒绝保护尚无干净恢复入口。实施保持原生load_data/load_userdata/组合load_datas，不新增金融状态序列化。

恢复仅接受同配置、同状态根、上一代确认干净关闭的原生状态。停止先关闭新目标并join全部策略/行情生产者，保留原交易owner完成查询/事件交接；原Standard全实例没有未决命令、未闭合提交组或未知结果，原订单表无活动单，再绑定原业务事件已经保存的状态文件并授下一代恢复。停止阶段没有额外save调用。元数据只绑定配置/原生文件摘要及关闭证明，消费后转为运行中标记；异常退出、篡改、配置变更或未决责任均拒绝，保持原文件和原Host/Journal身份。干净恢复不覆盖未知结果恢复，也不通过换空目录清除责任。产品同根两代及活动/unknown阻断的后继实证见[P21记录](../evidence/2026-10-29-native-clean-recovery.md)，其余恢复边界继续逐项验证。

实施顺序：先安装后多策略主调用链，再跑同根两代原生恢复，之后覆盖活动单/未知命令/状态损坏和并发关闭，最后独立审查、安装身份和文档检查。框架核心保持只读；若原公开save/load接缝不足，先提交必要性与准确范围供用户批准。

## 续接：重启与关闭边界

2026-10-28继续实际开发。既有12案及独立审查按原输入保留；新增[STQ-P18](../specs/native-qmt-standard-trader.md#stq-p18-输出根单写者与两代停止边界accepted开发中)为自有Session增加输出根独占租约，修复不同进程同时通过“空目录”检查并写原JSON的窗口。完整close释放；Parser/Reader或策略删除pending均保留至确认/进程退出。该文件仅为OS租约，不新增金融事实。

受控验证使用两个实际原生进程：首代产生原两策略JSON并正常停止；次代读取同一输出根时在引擎/行情初始化前明确拒绝，保留全部原文件并且SDK提交0。额外动态验证跨进程租约争用、Parser/Reader pending及在途策略回调关闭的join/删除顺序。最终[17案及独立full证据](../evidence/2026-10-28-multi-strategy-lifecycle.md)全部通过，安装公共头消费亦通过；当前固定集合及拒绝/关闭边界为development-verified，自动恢复、人工混用及生产资格继续pending-verification。

自动恢复的事实缺口已定位：Standard当前部分提交组/未决身份驻留本进程；新进程的完整券商查询不能证明先前未知请求绝未执行。后续恢复应沿原Host/Journal命令身份及原WT策略状态接续，先补契约和完整行为证明。当前保持同根拒绝，避免空目录、空查询或进程健康绕过未决责任。

具体待决策事项：若产品要支持自动恢复，需要确认覆盖“已确认无未决责任的干净停止”还是同时覆盖“异常退出及结果未知命令”；后者需要原命令身份恢复整链。若产品要支持同标的人工混用，需要确认手工保留目标及人工订单取消归属。上述选择分别影响恢复/混用范围，当前多策略固定集合与安全拒绝开发可独立完成。
